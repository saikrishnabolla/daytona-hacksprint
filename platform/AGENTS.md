# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

Use separate pages for the run workspace, finding details, shared memory, and integrations. Keep the selected Aikido-inspired layout dense and make sponsor activity visible in its relevant workflow.

Typography uses the shared system font and 12/13/14/16/20/28px tokens in public/typography.css. Use monospace only for commands, code, and technical values. Do not shrink text to fit dense layouts; allow wrapping, scrolling, or taller sections.

## Live-run architecture (decided)

- **One sandbox per run.** The target app and OWASP ZAP run together in a single Daytona sandbox and talk over `http://127.0.0.1:<port>`. A sandbox cannot reach another sandbox's preview URL (the proxy resolves to an internal CGNAT address and resets), so a separate scanner sandbox can never see the target.
- **Worker image.** Every target uses one image = `ghcr.io/zaproxy/zaproxy:stable` + git + Node 22 + python3. Juice Shop is baked in via `COPY --from=bkimminich/juice-shop`; repo targets are cloned at runtime; the synthetic fixture is uploaded.
- **Preview interstitial.** Daytona serves a "Preview URL Warning" page to *browsers* before proxying to the app. The browser verifier must pre-seed the `daytona-preview-page-accepted=true` cookie (see `seedPreviewConsent` in `server/sponsors.mjs`) or it only ever sees the warning page. Plain `curl` bypasses it, which is why host-side checks pass while the browser agent fails.
- **Repair loop semantics.** "Blocked" means the attack produced no dialog, the response was 2xx, and a normal search still works — not that the raw payload string appears in the DOM.
- **Targets.** `juice-shop` (real High-severity finding, no clean one-line fix), `demo-repo` (any git repo: clone → install → start → scan → patch → retest), `synthetic-help-center` (offline fixture with a known reflected XSS and a one-line patch).
- **Repo demo target.** The `demo-repo` target points at the standalone `demo-repo/` app — an **authenticated** Express app (`analyst@acme.test` / `demo1234`) with several planted issues: reflected XSS on `/search` (public) and `/dashboard` (authenticated), an off-site redirect on `/go`, and an IDOR on `/notes/:id`. The one-line fix (`const termHtml = term` → `escapeHtml(term)`) covers both XSS sinks. Set `DEMO_REPO_URL` for the clone-only path, or `DEMO_REPO_LOCAL_DIR` to upload a local checkout (offline fallback / rehearsal). Rehearse with `npm run demo:chain -- demo-repo`.
- **Authenticated scanning.** ZAP logs in over HTTP to grab the session cookie, seeds the URLs with that cookie (so the private `/dashboard?q=` node lands in the Sites tree authenticated), then runs the active scan. Do **not** enable ZAP forced-user mode: the "High Level Insights" feature counts auth failures on the public URLs and shuts ZAP down mid-scan. The browser verifier logs in with the same credentials before visiting the proof URL.
- **Parallel runs.** A "run" is one target in one sandbox (app + ZAP colocated). `POST /api/runs` fans out to N sandboxes **in parallel** and `/api/runs/:id/:step` drives one run's `scan → verify → propose → apply-fix → retest → memory → trace`; `/api/run/*` remains the single "primary" run for the simple flow. Each run tracks a `stages` object (`daytona/zap/anchor/bedrock/surrealdb/arize`) that the UI renders as a sponsor timeline. `GET /api/fs/dirs` powers the UI's folder picker; a picked local checkout becomes an ad-hoc target via `createRepoTarget` (reusing the demo-repo conventions: npm install → npm start → :3000 → `/health`).
- **Daytona caps.** The org allows **10 GiB total memory** and **30 GiB total disk**, so ad-hoc repo sandboxes request `REPO_MEMORY` (default 2 GiB) / `REPO_DISK` (default 8 GiB) rather than the demo target's 4 GiB / 10 GiB — that is what lets three boot side by side (3 × 8 = 24 GiB disk). Orphan sandboxes are the usual cause of `Total disk limit exceeded`: the `runs` map is in-memory, so a server restart forgets sandboxes that are still alive. Run `node server/daytona-purge.mjs` (add `--purge`) to list/delete them by the `project: daytona-hacksprint` label.
- **Runners.** `npm run demo:scan -- --target <id>` = provision + scan. `npm run demo:chain -- <id>` = the full loop (scan → Anchor verify → Bedrock propose → apply fix → Anchor retest → memory → trace). Requires `npm run server` on :8787. The UI's **Run full demo** button drives the same loop through the API — once per selected repository, all in parallel.

## Live console (decided)

- **The home route is a 5-step wizard, not one mashed screen.** `src/components/LiveWizard.tsx` (with `live-wizard.css`) is the home experience. The steps are **Overview → Agents → Issues → Fix & verify → Report**, one concern per screen with Next/Back. Step 1 is a GitHub-style connect card (real `GithubLogo`) plus a working local-folder picker, and the primary CTA is **Run tests** — never "provision sandboxes". Step 2 (**Agents**) shows all three sandboxes booting with their own live terminal + sponsor timeline, plus the **Anchor Browser** panel. Step 3 is a plain issues table with auto-fixable checkboxes (`pluginId === '40012'`); everything else is tagged Manual. Step 4 applies the Bedrock repair and shows the **captured** before/after frames; step 5 is the report. The wizard keeps `sessionIds` so its rail only ever shows its own runs.
- **Copy is intentionally minimal.** No "authorized targets only", "not sample data", "prove runs against your own repositories", or other qualifiers/explanatory footers. Say what the product does and stop.
- **Do not present static sample data as live — and do not fabricate evidence either.** `src/data.ts`, `Workspace.tsx`, `FindingInspector.tsx` and `LiveRunPanel.tsx` are deleted; `Pages.tsx` (`/findings`, `/memory`, `/integrations`) now reads `GET /api/runs` + `GET /api/health` and shows live values. The earlier Arize spans were synthesized (`buildSpans` faked every stage at start+15s) — that is fixed: `setStage` records a real start/end **window per stage invocation** (`timings[key]` is a list, so the anchor stage emits both `anchor.verify-xss` and `anchor.retest-xss`), `buildSpans` derives spans from those windows, and `traceRun` stores the exact spans it sent so the UI lists the **real** trace (name/kind/duration), not a count.
- **Anchor evidence is now real and durable.** The live-view URL (`https://live.anchorbrowser.io/inspector.html?…`) has no `X-Frame-Options`/CSP so it can be iframed, but it only works while the session is alive, and the VNC websocket often fails (403) leaving a black frame. `verifyXss` therefore also captures a PNG over the same CDP connection and returns `screenshotBase64`; `index.mjs` writes it to `tmpdir()/pentest-proofs/<runId>-<kind>.png`, caches it, and serves `GET /api/proof/:runId/:kind` (`verify`/`retest`) from disk first, cache second. Frames are **not** deleted on run cleanup, so they survive cleanup and a server restart. The wizard shows the captured frame as the primary evidence (live iframe/link is secondary), and only the finding Anchor actually **Confirmed** carries frames.
- **Orphans purge on boot.** Because the `runs` map is in-memory, restarting the API strands any live sandboxes (they keep consuming the 30 GiB disk cap and cause `Total disk limit exceeded` on the next run). `server.listen` now calls `purgeOrphanSandboxes` (exported from `server/daytona.mjs`, filters `daytona.list({ labels: { project: 'daytona-hacksprint' } })`) so a restart reclaims them automatically. `server/daytona-purge.mjs [--purge]` remains for manual use.
- **Wizard progress survives navigation.** The home wizard stays **mounted** (hidden, not unmounted) when other tabs are active, so an in-flight run and the current step are preserved; `step`/`sources`/`sessionIds`/`picked` are also mirrored to `sessionStorage` and only resumed on reload if the server still knows those run ids.
- **Verify vs retest are separate.** `verifyRun` writes `verification`; `retestRun` writes `retest` (it does **not** overwrite `verification`). Otherwise the post-fix `confirmed:false` would erase the pre-fix exploit proof.
- **SurrealDB record is surfaced.** `recordMemory` already read the record back; the UI now shows the actual `memory.record` (finding, endpoint, identity fields, `recordedAt`, `valid`) on the Memory page and in the report.
- **Anchor connection can go stale.** The cached CDP connection (`browser`) and Anchor session (`session`) outlive a run; if the session idles out or the CDP socket drops, the next `verifyXss` throws `browser.newContext: Target page, context or browser has been closed`. `ensureBrowser()` in `server/sponsors.mjs` checks `browser.isConnected()`, reconnects, and on failure drops the dead session and creates a fresh one before retrying. Without it, a second run silently never confirms (findings stay "Needs verification", anchor stage stuck `active`).
- **Dev-only scripts** live in `server/` (`shots-new.mjs`/`record.mjs` screenshot the UI, `wizard.mjs` drive all 5 steps, `drive.mjs` drive one run headlessly and print every step plus the proofs/memory/trace, `daytona-purge.mjs` list/delete sandboxes). They use the cached Playwright Chromium (`node node_modules/playwright-core/cli.js install chromium`).
